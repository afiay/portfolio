Explore Carthago's code & README ↗
Engineering notes +
Problem
Raw network events are hard to turn into security and troubleshooting observations someone can explain. Centralising logs across systems usually takes several tools, with upfront integration work and ongoing maintenance. 55% of surveyed security leaders say they have too many point solutions, 45% use six or more security tools, and 63% name operational cost as their biggest pain point.
Constraints
Windows desktop capture, varied protocols, noisy inputs, and no budget for a full logging stack. I also had to keep recorded evidence separate from interpretation.
Decision
Separate acquisition, protocol and flow inspection, security signals, and presentation. Keep one traceable log trail instead of adding tools. Build documentation from that trail: every capture, alert, and change leaves a timestamped record, and my notes are written from it. Interpretation is added by hand and labelled as such.
Verification
Document expected behavior with tests and repeatable samples. Inspect false positives and UI empty states before calling a rule dependable. Strip sensitive data before anything is documented, and flag where logging was incomplete.
Learning
Visibility only matters when an operator can tell what happened, why it was flagged, and what remains uncertain. Logs show events, not intent, so the “why” still needs a human, clearly marked.

Survey context: These statistics come from a survey of 506 security leaders and practitioners at organizations with more than 500 employees, reported in Sumo Logic’s 2026 Security Operations Insights Report. Sumo Logic is a SIEM vendor.

Engineering notes +
Problem
Operators juggled six separate tools: GPS, alerts, statistics, on/off control, Grafana, and Home Assistant. Each tool needs maintenance, and each switch costs attention. A 2022 study of 137 users found about 1,200 app toggles a day and roughly 9% of work time spent reorienting. In a separate 2018 study, workers using 30 or more applications in a shift had a 28% higher error rate than those using fewer apps.
Constraints
The existing platform and database had to stay intact, integrating only through existing REST services.
Decision
A plugin-based platform where each user picks what they see: alerts, GPS, or any chart. Switches and automation run from the same interface, and existing integrations connect as plugins. Result: 6 windows reduced to 1, an 83% reduction in separate interfaces.
Verification
Compared windows needed per task before and after. Checked API mappings, permissions per role, and loading, empty, and error states.
Learning
Centralising means giving people one place to choose what matters, while respecting what already works.

Research context: Murty, Dadlani & Das, Harvard Business Review (2022) studied 137 users across three companies. The 28% error-rate comparison comes from Workplace Insight's report (2018) on Pegasystems research. These are external findings, not measured productivity or error-rate improvements at IoT Open. The 83% figure describes the reduction in separate windows (6 to 1).

NETWORK AUTOMATION & ASSESSMENT 04
Independent · documented Cisco GNS3 lab

Ansible Patch Management

I built a read-only Cisco IOS assessment workflow in GNS3 using Ansible. It discovers device state, backs up the running configuration, reviews security settings and a Cisco field notice, and produces evidence for a human to assess before any change.

AnsibleCisco IOSGNS3Jinja2SHA-256
CONTRIBUTION

Built separate discovery, backup, security assessment, risk review and advisory playbooks, plus reporting templates and an evidence manifest.

CONTEXT

Read-only educational lab. No IOS upgrades, configuration changes, automatic approvals or production deployment. The manifest is run separately from site.yml.

Explore the Ansible playbooks & README ↗
Engineering notes +
Problem
Assessing a device and preparing a safe patch decision requires more than checking its IOS version. Configuration, exposure, applicability and reliable evidence must be reviewed together.
Constraints
One Cisco 7200 IOS router in an isolated GNS3 environment, controlled over SSH from Ubuntu. The assessment must not alter the device.
Decision
Separate discovery, backup, security review, risk inputs and Cisco FN70489 prerequisite checks into focused Ansible playbooks. Generate Markdown evidence reports and SHA-256 manifests for later comparison.
Verification
Use IOS show-command evidence, review the resulting configuration snapshot and report output, validate assessment inputs and distinguish observed status from advisory applicability.
Learning
Automation should make decisions traceable, not silently make them. Patch execution, approval, restore and validated failover remain separate future steps.

Source: Ansible Patch Management documentation.
